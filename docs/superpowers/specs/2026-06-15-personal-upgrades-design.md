# Personal Upgrades, Teleport Warmup & Homes UI Design

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Add a "Personal" upgrade category spanning HavenCore (AFK timer) and HavenTeleport (home/warp/shop slots), a generic teleport warmup system with action bar animation, and a cleaner /homes dialog.

**Repos affected:**
- `HavenAPI` (HavenCore) — AFK upgrade, AfkManager integration
- `HavenTeleport` — slot upgrades, warmup system, /homes dialog redesign

## 1. Upgrade System

### Architecture

Both repos use HavenCore's existing `HavenUpgradeService` / `UpgradeProvider` pattern. No new persistence or service layer needed — everything rides existing infrastructure.

**Upgrade model:**
```
UpgradeDefinition(id, providerId, category="personal", List<UpgradeLevel>)
UpgradeLevel(level: int, displayName, List<requirement>, List<effect>, metadata)
```

Requirements and effects are config-driven per level (type + metadata map). Cost type configurable per tier: Vault money, tier permission, or both.

Player current level: `upgradeService.currentLevel(UUID, upgradeId)` → int (0 = not purchased).

### HavenCore — AFK Timer Upgrade

**Upgrade id:** `afk-timer`  
**Category:** `personal`  
**Provider:** `CoreUpgradeProvider` (create if not exists; otherwise add to existing)  
**Levels:** I–V (configurable tier count in `upgrades.yml`)

Each level defines:
- `effects: [{type: "afk-duration", values: {minutes: "30"}}]` — added time beyond base timeout
- `requirements`: configurable per level (e.g., Vault money cost)

**AfkManager integration:**

`AfkManager` resolves effective AFK timeout as:
```
effectiveTimeout = base_timeout + afk_config.bonusMinutesForLevel(currentLevel(uuid, "afk-timer"))
```

`AfkSettings` holds a list of bonus values indexed by upgrade level (level 0 = no bonus). AfkManager reads `upgradeService.currentLevel(uuid, "afk-timer")` and looks up the bonus directly from its own config — no dependency on the upgrade effect system at runtime.

### HavenTeleport — Slot Upgrades

**Provider:** `TeleportUpgradeProvider` implements `UpgradeProvider`  
**Category:** `personal` (same category, appears alongside AFK in /upgrades Personal section)

| Upgrade id   | Governs          | Levels |
|--------------|------------------|--------|
| `home-slots` | max home count   | I–V    |
| `warp-slots` | max player warps | I–V    |
| `shop-slots` | max shop count   | I–V    |

Each manager resolves max slots as:
```
maxSlots = config.baseSlots + (currentLevel(uuid, upgradeId) * config.slotsPerLevel)
```

`TeleportUpgradeProvider` is registered with HavenCore's upgrade service on plugin enable (existing hook already implemented).

## 2. Teleport Warmup System (HavenTeleport)

### Service API

```java
// TeleportWarmupService
void startWarmup(Player player, String commandKey, Runnable onComplete)
void cancelWarmup(Player player)
boolean hasActiveWarmup(Player player)
```

`commandKey` maps to duration in `teleport.yml` (e.g., `warmup.home: 3s`, `warmup.warp: 2s`).

Internal state: `Map<UUID, WarmupTask>` where `WarmupTask` holds the repeating `BukkitTask` and `onComplete` callback.

### Action Bar Animation

Repeating task every 2 ticks. Format (configurable chars in `teleport.yml`):
```
Teleporting ██████░░░░ 3s
```
- Filled char: `█` (configurable)
- Empty char: `░` (configurable)
- Bar width: 10 (configurable)
- Countdown suffix in seconds

On complete: action bar cleared, `onComplete` fires, teleport executes.  
On cancel: action bar cleared, configurable cancel message sent to player.

### Cancellation Triggers

| Event | Condition | Behavior |
|-------|-----------|----------|
| `PlayerMoveEvent` | position delta > 0 (head rotation excluded) | cancel warmup |
| `PlayerQuitEvent` | always | cancel warmup |
| `EntityDamageEvent` | configurable `cancel-on-damage: true` | cancel warmup |

### Bypass

Permission: `haventeleport.warmup.bypass.<commandKey>` (e.g., `haventeleport.warmup.bypass.home`)  
If present: teleport fires immediately, no action bar animation.

### Integration

Each teleport command checks bypass first. Without bypass:
```java
warmup.startWarmup(player, "home", () -> teleportService.teleport(player, target));
```

## 3. /homes Dialog Redesign (HavenTeleport)

### Main Dialog (`/homes`)

- Title: `Homes`
- Body: `Homes (used/max)` — e.g., `Homes (3/5)`
- Buttons (2-column layout):
  - One button per home: label = `★ homename` (main) or `homename`
  - Tooltip: world + coordinates
  - `+ Add Home` button always visible; clicking it closes the dialog and executes set-home at the player's current location (equivalent to `/sethome <auto-generated-name>`). If at slot cap → no-op action + message `"Home slots full. Upgrade in /upgrades."` If in an invalid location (e.g., mid-air) → message from existing sethome validation.
- `multiAction(buttons, null, 2)`

### Per-Home Sub-Dialog

Opens when clicking a home button.

- Title: home name
- Body: world + coordinates as plain text
- Buttons:
  - `Teleport` — triggers warmup → teleport
  - `Set as Main` — hidden if already main home
  - `Delete` — confirms then deletes
  - `← Back` — reopens main homes dialog

No "Edit" label anywhere. Each action named for what it does.

### Max Slots Resolution

```java
int maxSlots = config.baseHomeSlots
    + upgradeService.currentLevel(player.getUniqueId(), "home-slots")
      * config.homeSlotsPerLevel;
```

Same pattern in warp and shop dialogs when those are redesigned.
